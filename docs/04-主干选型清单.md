# 04 · 主干选型清单（待你确认）

> 用法：每个决策点给出**候选项**、**我的推荐**和**换成别的代价**。你只需在最后一节的表格里填选择；
> 没填的我就按"推荐"执行。标 ★ 的是**会改变其它选项**的关键分叉。

当前约束（已确认）：先用**转播视频**练手 → 先跑通**算法原型** → 机器只有 **CPU + Radeon 780M 核显** → 未来场地为**室外天然草、白天**。

---

## ★ D0. 许可定位（最先决，决定 D1/D3/D4 能不能用）

| 选项 | 含义 | 代价 |
|---|---|---|
| **A. 现在就按闭源商用约束选型** | 全程只用 MIT/Apache-2.0/BSD 组件 | 放弃 ultralytics 生态与 boxmot，检测器要换 RT-DETR/YOLOX，跟踪要自写，起步慢 1–2 周 |
| **B. 原型期不设限，平台化时再换**（推荐） | 现在用最省事的（YOLOv8n + ByteTrack），但**架构上把检测器/跟踪器做成可替换接口** | 需要提前设计接口，约多花半天；换来原型速度 |
| **C. 确定开源 / 仅内部使用，不关心许可** | 一直用 AGPL/GPL 组件 | 无 |

> 推荐 B 的理由：你现在要的是**验证可行性**，而"可替换接口"这件事无论如何都该做——它同时也是 D1/D3 的升级路径。

## ★ D1. 球员/裁判/门将 检测器

| 选项 | 许可 | 本机实测 | 备注 |
|---|---|---|---|
| **YOLOv8n / YOLO11n（ultralytics）**（推荐原型） | AGPL-3.0 | 26.7 / 28.7 ms@640 | 生态最好、教程最多、Roboflow 有现成足球数据集可直接微调 |
| RT-DETR（官方仓库） | **Apache-2.0** | CPU 上比 YOLOn 慢（未实测） | 闭源路线的首选替代；精度通常更高 |
| YOLOX | Apache-2.0 | 未实测 | 成熟但偏老 |
| MMDetection（含 DINO/DETR 系） | Apache-2.0 | 未实测 | 全家桶，配置复杂 |
| torchvision Faster R-CNN | BSD-3 | 慢 | 最保守，精度一般 |

**建议**：原型用 `yolov8n` → 需要闭源时切 RT-DETR（接口不变，只换权重与后处理）。
**另一条重要事实**：无论选哪个，最终都要**用你自己的球场画面微调**——现成权重都是转播/公开数据集训的，域外会掉点。

## ★ D2. 球检测（必须与球员分开）

| 选项 | 说明 |
|---|---|
| **独立小模型 + 切片推理**（推荐） | 球单独训一个 `yolov8n`，用 `sv.InferenceSlicer(slice_wh=(640,640))` 切片 + `nms 0.1` 找小目标；低 conf（0.05–0.1）保召回 |
| 一个模型多类别 | 实现最简，但小球与大目标尺度冲突，实测会崩 |
| 零样本检测（GroundingDINO/DINO 系） | 免训练，但 CPU 上太慢，不适合整场 |

**建议**：独立模型 + 切片。参考 `third_party/roboflow-sports/examples/soccer/main.py:227-235`。

## ★ D3. 多目标跟踪

| 选项 | 许可 | 说明 |
|---|---|---|
| **supervision `ByteTrack`**（推荐原型） | MIT | 零成本、`roboflow/sports` 就用它；**实测 300 帧碎出 93 个 ID**，需调参（`minimum_consecutive_frames`、`lost_track_buffer`） |
| **自写 OC-SORT / BoT-SORT 关联**（推荐进阶） | 自研 → 无许可问题 | SportsMOT 上 OC-SORT 71.9 / BoT-SORT 68.7 vs ByteTrack 62.8 HOTA，且**去掉卡尔曼预测反而 +7.4**；CMC 部分就是几十行 OpenCV |
| boxmot（15+ 跟踪器开箱） | **AGPL-3.0** | 技术最省事，但污染服务端；只适合 D0 选 C 的情况 |
| Deep-EIoU | 需自实现 | 学术最强（75.3 HOTA），核心是"迭代扩展 IoU"，无官方 pip 包 |
| sportslabkit 的 SORT/DeepSORT | GPL-3.0，2023-12 停更 | 不推荐 |

**建议**：ByteTrack 起步 → 按 OC-SORT 论文自写关联（同时解决 AGPL 问题）。**无论选哪个，都必须先接上 `sn-trackeval` 评估**，否则无法判断改动是否变好。

## D4. ReID 特征（治 ID 跳变）

| 选项 | 许可 | 说明 |
|---|---|---|
| **OSNet x0.25（torchreid）**（推荐） | MIT | CPU 上很快；但**行人域（MSMT17）预训练**，球场跨域有落差 |
| OSNet x1.0 | MIT | 更强更慢，同域问题 |
| PRTReID / BPBReID | 随 sn-gamestate，GPL | 足球域效果最好，但权重从 Zenodo 拉、依赖重 |
| 不用 ReID，只靠时空约束 + 人工确认 | — | 最省事，且**画质差时往往比 ReID 更靠谱** |

**建议**：阶段 2 再做；先 OSNet x0.25 作辅助证据，主导权交给"时空约束 + 关键节点人工确认"。

## ★ D5. 球队区分

| 选项 | 许可 | 优缺点 |
|---|---|---|
| **SigLIP + UMAP(3) + KMeans(2)**（推荐主方案） | MIT | 通用、无需人工填色；**权重自动从 HuggingFace 下载**；但每次要重跑 fit（应改成拟合后落盘），且门将需单独按队心归属 |
| HSV 去草 + 上半身主色 + 人工锚色最近邻 | 自研 | `songminkyu` 路线；极快极稳、可复现；代价是每支队要人工填一次球衣 RGB |
| 球衣号码 OCR 认队 | — | **不可行**，自有摄像头远端号码区只有几十像素 |

**建议**：SigLIP 为主 + HSV 锚色作**交叉校验与兜底**（两者不一致的帧标出来人工看）。门将按"离哪队质心近"归属。

## D6. 球场标定（画面 → 米制坐标）★技术上最关键，但答案基本唯一

| 选项 | 说明 |
|---|---|
| **球场关键点检测模型 + 32 点配置 + 每帧动态单应 + 矩阵指数平滑**（推荐） | `songminkyu` 路线。**转播镜头一直在动，必须动态单应**；自建固定机位同样适用且更简单。顺带解决了相机运动补偿，**不需要光流**（省 60.7 ms/帧） |
| 手工点 8–12 个关键点 → `findHomography` | 最稳、零依赖，适合**固定机位**；缺点是每场要人工点一次、镜头一动就失效 |
| PnLCalib 离线出 H | GPL-2.0，只在转播数据上训练；建议**只当离线工具**，把输出的 H 当数据用 |
| 光流刚性平移补偿 | ❌ 不要用（本机 60.7 ms/帧比检测还贵，且参考项目实现有符号/陈旧特征点 bug） |

**建议**：关键点模型 + 动态单应（主）；手工标定做**初值与交叉校验**，并监控重投影误差当告警。

## D7. 坐标系与数据契约

- **坐标系统一用米制 105×68**。（`roboflow/sports` 是**厘米** 12000×7000，`sportslabkit` 是**米**，混用必错。）
- **落盘格式**：原型用 **Parquet**（列式、体积小、pandas/polars 直接读）+ JSON 存元数据与 H 矩阵；平台期再迁 SQLite/Postgres。
- **数据契约**（所有开源项目都缺这个，必须先定）：
  - `tracks.parquet`：`frame, timestamp, track_id, class, team, x_m, y_m, conf`
  - `ball.parquet`：`frame, timestamp, x_m, y_m, conf`
  - `calibration.json`：每 N 帧的 3×3 单应矩阵 + 重投影误差 + 时间戳

## ★ D8. 推理后端

| 选项 | 本机实测（YOLOv8n@640） | 说明 |
|---|---|---|
| **PyTorch CPU**（推荐原型） | 26.7 ms | 最省事，ultralytics 原生支持，改模型不用改代码 |
| **ONNX Runtime + DirectML**（推荐作为加速层） | **11.8 ms（2.3×）** | 用上 Radeon 780M 核显；**但没有任何开源项目支持**，需自写 ONNX 推理层 + NMS 后处理 |
| ONNX Runtime CPU EP | 57.2 ms | 未调优线程，不划算 |
| 云 GPU 批处理（AutoDL 等） | 依卡型 | 后期全量跑批可选；要算上传带宽 |

**建议**：原型 PyTorch CPU → 链路稳定后加一层 ONNX+DirectML 推理后端（把加速层和算法层解耦）。

## D9. 视频解码与抽帧

| 选项 | 说明 |
|---|---|
| **OpenCV `VideoCapture`**（推荐原型） | 最简单；端到端实测已含它的开销（12 FPS 那条） |
| PyAV / ffmpeg 管道 | 更快、能精确控制帧，瓶颈时可换 |
| 抽帧策略：逐帧 / `vid_stride` / 死球降采样 | 实测：逐帧整场 3.8 h → `vid_stride=3` 降到 1.1 h。**建议做成可配置**，默认逐帧调参、全量跑时抽帧 |

## D10. 评估体系（必须有，否则优化全靠感觉）

| 选项 | 说明 |
|---|---|
| **`sn-trackeval`**（推荐） | MIT，HOTA/DetA/AssA + GS-HOTA，纯 numpy，零 GPU |
| SportsMOT 的 TrackEval fork + `data/ref/sportsmot-val` gt | 数据 **CC BY-NC 4.0 非商业且禁再分发**；可当回归测试集 |
| 自建可视化对拍 | 必做，用于人工看 ID 跳变 |

## D11. 指标算法

| 决策 | 推荐 |
|---|---|
| 轨迹滤波 | **离线用 Savitzky-Golay**（零相位）、**在线用 One-Euro**；不要直接对原始坐标差分求速度 |
| 控球判定 | 球-人距离 + **滞后阈值** + **最短持续时间** + **双 grace**（抄 `songminkyu` 的球权模块） |
| 首期指标 | ① 总跑动距离 + 速度剖面 ② 控球时间占比 ③ pitch control / 位置热图 |
| 后置指标 | 阵型识别、传球估计（PathCRF 类） |
| 暂不做 | xG / xT / VAEP / PPDA / 传球成功率（依赖事件层，且 EPV 公开复现被质疑） |
| 必须声明的口径 | 控球率是"时间占比"还是"触球次数占比"；**低速段距离不可信**（专业系统 vs VICON 低速段偏差 −19.4%，总距离仅 0.4%） |

## D12. 工程形态

| 选项 | 说明 |
|---|---|
| **Python 包 + CLI + YAML/pydantic 配置**（推荐） | 可测试、可组合；单机批处理一场一个 job |
| 单体脚本 | 最快，但一周后自己看不懂（参考项目就是这种） |
| 直接上 FastAPI + 任务队列 | 现在过早，留好接口即可 |

## D13. 练手数据源

| 选项 | 说明 |
|---|---|
| **仓库自带样例视频**（推荐立刻用） | `third_party/Football-Vision/videos/Demo_Video.mp4`、`Football-Game-Possession-Tracking/input videos/*.mp4` |
| SoccerNet 系列 | 转播，需申请/可能签协议，GB 级 |
| **SoccerTrack v2** | 固定 4K 全景 + 米制真值，**唯一与你自建机位同赛道**的公开数据（需申请） |
| SportsMOT | 240 段，含足球航拍；仅非商业 |
