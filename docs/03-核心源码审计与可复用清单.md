## A. 教学级端到端项目

### A.1 `football_analysis`（abdullahtarek）— 不能当地基

**入口**：`football_analysis/main.py:12-84`，线性脚本，无编排层。
执行顺序：读视频 → `Tracker('models/best.pt')` → 检测+跟踪 → 位置提取 → 相机补偿 → 透视变换 → 球插值 → 速度距离 → 分队 → 球权 → 绘制 → 写视频。
（注意顺序颠倒：速度估计发生在分队/球权**之前**。）

**其余审计结论**（未逐条 grep，但来自源码通读，附位置）：
- `camera_movement_estimator/camera_movement_estimator.py:20-22`：光流特征点 mask 写死 `x∈[0,20)∪[900,1050)`；`:61-68` 取**最大位移**当全局平移（非中位数/RANSAC）；`:56` `calcOpticalFlowPyrLK` 的 `status/err` 被丢弃；`:74` `old_gray` 每帧更新但 `old_features` 仅在位移 >5px 时刷新 → 慢速平移段光流必然不收敛。
- `team_assigner/team_assigner.py`：直接对 **BGR** 做 KMeans（无颜色空间转换、无光照归一化）；球员**上半身**取色；四角像素投票定背景簇；`player_team_dict` 按 ID **永久缓存**；只用**第 0 帧**校准（`main.py:46-47`）。
- `player_ball_assigner/player_ball_assigner.py:7,18-20`：球中心到球员 bbox **左下/右下角**的较小距离，阈值 `70`（**像素**，与分辨率死绑）。
- `utils/video_utils.py:3-11`：整段视频全帧进内存（750 帧≈4.6 GB；整场 16.2 万帧 ≈ 1 TB）。
- `trackers/tracker.py:71-73`：进跟踪前把 goalkeeper 的 class_id 改写成 player（门将与球员共用 ID 空间）。
- `main.py:69`：首帧无球权时对空 list 取索引 → IndexError。

**可复用的只有两个思路**：`utils/bbox_utils.py` 的 `get_foot_position`（底边中点当落点）；"球到脚点最近距离"的球权度量（阈值要改成米制）。**代码不要抄进产品（无许可）。**

### A.3 `songminkyu-football-analysis` — 唯一值得细读的进化版

**做对的三件事**：
1. **单应性动态化**（`position_mappers/homography.py:50-52,67`）：把检出的球场关键点索引直接映射到 32 点标准场地坐标 → `cv2.findHomography` → `HomographySmoother(alpha=0.9)` 对 3×3 矩阵做指数平滑 → 脚点投影。**换机位仍可用**，且顺带解决了相机运动（镜头动则 H 跟着动），**因此不需要光流补偿**。
2. **球权判定达到可用水平**（`ball_to_player_assignment/ball_to_player_assigner.py`）：投影后按场地坐标算距离（阈值 10.0 场图像素）＋ **点球点屏蔽**（球中心靠近点球点关键点即作废，防点球点被误检为球）＋ **球速校验**（跳变过大判误检）＋ **双 grace period**（4 s 保留上一持球人 / 2 s 容忍球消失）。
3. **三线程流水线**（`utils/video_utils.py:184-188` Capture/Processing/Display + 队列），正确做法。

**要修的问题**：
- `speed_estimation/speed_estimator.py:30-31`：x/y 两轴像素→米比例不一致（像素比 1.5 对应场地比 2.0）→ **y 向速度系统性偏约 25%**。
- `ball_to_player_assigner.py:16` 的 fps 默认 30 未被真实 fps 覆盖 → grace 时长随素材漂移。
- `football_video_processor.py:112-113` 传入的关键点索引与注释不符（说点球点，实际传入的是角旗区索引 24）→ 屏蔽区挂错。
- `file_writing/tracks_json_writer.py:45-69`：每帧"读全量 + append + 全量写回"，长视频 O(n²) 写放大。
- `utils/video_utils.py:228`：`os._exit(0)` 强杀进程。分辨率写死 1920×1080。
- 权重需自训（`models/weights/` 在 `.gitignore` 内）。

### A.4 `Football-Vision`（Smasko7）— 工程化最好，但分队是坏的

**已复核** ✅：全仓 `TeamClassifier` 构造 3 处（`football_vision/modes/radar_frame.py:42`、`radar_video.py:33`、`team_video.py:18`），`predict()` 调用 3 处（`:68`、`:66`、`:46`），而 **`.fit()` 一次都没有调用** ✅。
对照 `roboflow-sports/examples/soccer/main.py:291,302`（先 `fit(crops)` 再 `predict(crops)`）✅。
且 `roboflow-sports/sports/common/team.py:111-112` 的 `predict()` 直接调 `self.reducer.transform(data)` 与 `self.cluster_model.predict(...)` —— UMAP 与 KMeans 在 `__init__` 中只构造未拟合 → **这三个分队模式一跑就抛 NotFittedError** ✅。

**可直接复用**：`football_vision/config.py` + `config.yaml` 的配置化范式（四家里最工程化）；`core/detection.py` 的 `split_detections` / `filter_keypoints` / `resolve_goalkeepers_team_id`（门将按"离哪队质心近"归属，实用）；`run.py` 的模式分发表 + 按模式懒加载。

**其它坑**：`sports/` 在仓库里是未初始化的 gitlink（空目录，无 `.gitmodules`），README 的 `pip install -e sports/` 会失败；默认依赖 Roboflow 云 API（离线不可用）。

## B. 框架级

### B.1 `roboflow-sports`（MIT）— 算法零件库，不是框架

`git clone` 后 `pip install` 源码安装（**PyPI 上没有 `sports` 包**）。全部代码只有 6 个文件，`sports/__init__.py` 为空，必须按子模块路径 import：

| 模块 | 导出 | 用途 |
|---|---|---|
| `sports/configs/soccer.py` | `SoccerPitchConfiguration` | 球场几何常量：**厘米**制 `width=7000, length=12000`，32 个 `vertices`（顺序须与关键点模型输出对齐）、`edges`、`labels` |
| `sports/common/view.py` | `ViewTransformer` | `cv2.findHomography` 封装（21 行），`transform_points()` 要求 Nx2 且 ≥4 点 |
| `sports/common/team.py` | `TeamClassifier`, `create_batches`, `SIGLIP_MODEL_PATH` | **SigLIP → UMAP(3 维) → KMeans(2)**；权重 `google/siglip-base-patch16-224`，HuggingFace 自动下载，无需 API key |
| `sports/common/ball.py` | `BallTracker`, `BallAnnotator` | 球位置平滑（`deque` 最近邻，**不是跟踪算法**）+ jet 色拖尾 |
| `sports/annotators/soccer.py` | `draw_pitch` / `draw_points_on_pitch` / `draw_paths_on_pitch` / `draw_pitch_voronoi_diagram` | 俯视小地图与 Voronoi |

**关键事实**：
- **跟踪器不在这个包里**，来自 `supervision`（`examples/soccer/main.py:254` `sv.ByteTrack(minimum_consecutive_frames=3)`）。
- 球检测用 `sv.InferenceSlicer(slice_wh=(640,640))` 切片推理 + `.with_nms(0.1)` 解决小目标（`main.py:227-235`）。
- 类别约定硬编码在 `main.py:23-26`：`ball=0, goalkeeper=1, player=2, referee=3`。
- **可以换成自建摄像机的标定点**：只需自备"图像点 ↔ `CONFIG.vertices` 子集"的对应关系，照抄 `main.py:137-143` 四行即可，不依赖它的 pitch 检测模型。
- **只画图不落盘**：`main.py` 没有任何 CSV/JSON 导出，只画到视频上。
- `TeamClassifier` 的拟合结果**不落盘**，每次运行都要重新 `fit()`。

### B.2 `SoccerTrack` / `sportslabkit`（GPL-3.0，2023-12 停更）— 抄设计，别抄代码

- **数据模型是最值得借的**：`BBoxDataFrame`（三级列索引 TeamID/PlayerID/Attributes，行为帧）与 `CoordinatesDataFrame`；`load_df()` 自动识别 **MOT / SoccerTrack CSV / Labelbox ndjson / GPS** 四种格式；`to_codf(H, method='bottom_middle')` 一键转球场坐标。
- **抽象设计**：`MultiObjectTracker(window_size, step_size, max_staleness, min_length, callbacks)` 基类统一管理 tracklet 生命周期（`mot/base.py:52`），子类只实现逐帧 `update()`；`load('YOLOv8x')` 走子类枚举自动发现模型，自己继承 `BaseDetectionModel` 即可被找到。
- **坐标系是米**：`camera/camera.py:25-26` `x_range=(0,105), y_range=(0,68)`，且有 `video2pitch` / `undistort_points`（鱼眼/张氏标定）。
- **多摄像机只是 `load_cameras()` 批量构造**，**没有**跨相机融合/三角化/全局 ID 统一。
- **依赖面极宽**（40+，含 `labelbox`/`kaggle`/`optuna`/`pytorch_lightning`），装进生产环境很痛苦；GPL-3.0 且停更两年。
